# Документація зі статичного аналізу коду (Linting) — AnimeGallery

Цей документ описує підхід до статичного аналізу коду в проєкті **AnimeGallery**, обрані інструменти linting, їх конфігурацію, а також інструкції з запуску перевірок. Метою впровадження linting є підвищення якості коду, забезпечення єдиного стилю та раннє виявлення помилок.

---

## 1. Обрані інструменти та причини вибору

У проєкті використовується роздільний підхід до статичного аналізу для frontend та backend частин.

### Frontend — ESLint

**ESLint** використовується для аналізу JavaScript та React-коду.

#### Причини вибору:
- є стандартом де-факто для React-проєктів
- підтримує перевірку React Hooks
- має велику екосистему правил та плагінів
- інтегрується з більшістю редакторів коду, включаючи Visual Studio Code

#### Основні задачі ESLint:
- запобігання логічним помилкам у компонентах
- контроль використання React Hooks
- виявлення невикористаних змінних
- забезпечення єдиного стилю коду

---

### Backend — Ruff

Для Python/Django частини використовується **Ruff** — сучасний високопродуктивний лінтер.

#### Причини вибору:
- значно швидший за Flake8 та pylint
- поєднує в собі функціональність Flake8, isort та частково pylint
- забезпечує перевірку відповідності стандарту PEP 8

#### Основні задачі Ruff:
- перевірка стилю Python-коду
- сортування імпортів
- виявлення логічних помилок та невикористаних змінних

---

## 2. Базові правила linting

### Правила ESLint

У файлі `eslint.config.js` налаштовані такі ключові правила:

#### `eqeqeq` — Error
Забороняє використання нестрогого порівняння (`==`) та дозволяє лише суворе (`===`).  
Це запобігає помилкам, пов’язаним з неявним приведенням типів у JavaScript.

#### `no-unused-vars` — Warning
Попереджає про змінні, які були оголошені, але не використовуються.  
Допомагає підтримувати код чистим та зрозумілим.

#### `no-console` — Warning
Обмежує використання `console.log` та інших методів консолі у фінальній версії додатку.

#### Ігноровані директорії
ESLint не перевіряє:
- `node_modules/`
- `dist/`
- інші згенеровані файли збірки

---

### Правила Ruff

Конфігурація знаходиться у файлі `ruff.toml`:

```toml
line-length = 120
select = ["E", "F", "W", "I"]
```

#### Пояснення:

- **E** — помилки стилю відповідно до PEP 8
- **F** — логічні помилки та невизначені змінні
- **W** — попередження
- **I** — правила сортування імпортів

#### Ігноровані директорії

Ruff не перевіряє:
- `venv/`
- `__pycache__/`
- Django-міграції (`*/migrations/*`)

---

## 3. Інструкція з запуску лінтера

### Запуск ESLint (Frontend)

З кореневої директорії проєкту:

```bash
npm run lint
```

Ця команда:
- перевіряє всі `.js` та `.jsx` файли
- виводить список помилок та попереджень у термінал

---

### Запуск Ruff (Backend)

Перед запуском необхідно активувати віртуальне середовище Python:

```bash
venv\Scripts\activate
```

#### Перевірка коду

```bash
ruff check .
```

Команда виконує статичний аналіз усіх Python-файлів у проєкті.

---

#### Автоматичне виправлення помилок

```bash
ruff check . --fix
```

Ruff автоматично:
- сортує імпорти
- видаляє невикористані імпорти
- виправляє форматування

Ці зміни є безпечними та не впливають на логіку програми.

---

## 4. Переваги використання linting у проєкті

Використання статичного аналізу дозволяє:

- виявляти помилки ще до запуску програми
- підтримувати єдиний стиль коду
- спрощувати рев’ю коду
- зменшувати кількість багів у production

---

## 5. Рекомендований процес роботи

Перед кожним комітом рекомендується виконувати:

```bash
npm run lint
ruff check . --fix
```

Це дозволяє підтримувати кодову базу в чистому та стабільному стані.
