# Звіт про аналіз продуктивності системи (Performance Audit)

## 1. Методологія тестування

Для об'єктивної оцінки швидкодії системи було проведено стрес-тестування на великому масиві даних та профілювання ключових сценаріїв взаємодії.

### Інструментарій

**Backend Profiling:**  
Django Debug Toolbar (аналіз SQL-запитів, Explain Plan) та Pyinstrument (CPU).

**Frontend Profiling:**  
Chrome DevTools (вкладка Network та Performance) для вимірювання Time to First Byte (TTFB) та часу блокування DOM.

### Тестове середовище
локальний сервер розробки, БД SQLite/PostgreSQL.

### Обсяг даних
100, 1000 та 10000 записів аніме-тайтлів (згенерованих через кастомний скрипт `generate_anime`), користувацькі оцінки та статуси.

---

## 2. Результати вимірювань (Baseline Metrics)

Дані отримані до впровадження оптимізацій при завантаженні повного каталогу (1000 записів).

### Сценарій А: Повнотекстовий пошук
`?search=Anime`

- Загальний час відповіді (Total Time): **~89.08 ms**
- Час виконання SQL (SQL Time): **3.12 ms**
- SQL Queries: **3 запити**

### Сценарій Б: Завантаження загального списку аніме (List View)

- Загальний час відповіді (Total Time): **504.98 ms**
- Час виконання SQL (SQL Time): **2.20 ms**
- Затримка серіалізації (Serialization Overhead): **~490 ms**
- Обсяг переданих даних (Payload): **703 KB** (критична аномалія)
- Час блокування інтерфейсу (DOMContentLoaded): **3.67 сек**

---

## 3. Виявлені проблеми з продуктивністю (Hotspots)

На основі отриманих метрик ідентифіковано ключові "гарячі точки".

### 3.1. Критична проблема Serialization Bottleneck

Найбільш вагома точка деградації продуктивності на бекенді.

**Суть:**  
при отриманні списку з 1000 аніме база даних віддає результат майже миттєво (2.20 ms), але ORM та Django REST Framework витрачають пів секунди на конвертацію Python-об'єктів у JSON.

**Доказ:**  
дельта між SQL Time та Total Time складає понад 500 ms; CPU-профілювальник вказує на `AnimeSerializer`.

**Наслідки:**  
експоненціальне зростання часу відповіді при збільшенні кількості карток аніме.

---

### 3.2. Навантаження на мережу та DOM-дерево

**Опис:**  
передача масивного JSON-файлу (703 KB) перевантажує мережевий канал, а спроба відрендерити 1000 компонентів `AnimeCard` одночасно блокує браузер.

**Причина:**  
відсутність серверної пагінації.

**Наслідки:**  
"заморожування" інтерфейсу на 3.67 секунди, дуже низький показник TBT (Total Blocking Time).

---

### 3.3. Ефективність пошуку (Full Table Scan)

**Опис:**  
пошук за параметром `?search=Anime` ініціює повне сканування таблиці.

**Доказ:**  
аналіз плану виконання (Explain Plan) показав використання операторів `LIKE %Anime%` без застосування індексів (Sequential Scan).

**Наслідки:**  
відсутність індексів на текстових полях призведе до критичного сповільнення пошуку при накопиченні десятків тисяч аніме.

---

### 3.4. Оверхед запиту COUNT(*) при пагінації

**Опис:**  
виявлено деградацію продуктивності базового класу `PageNumberPagination` на обсягах у 10000+ записів.

**Наслідки:**  
прихована затримка (~7.91 ms) на виконання підрахунку загальної кількості рядків для формування кількості сторінок.

# Оптимізація розміру застосунку та фронтенд-бандла

Для покращення швидкості початкового завантаження застосунку (метрики LCP та TBT) було реалізовано комплекс заходів з оптимізації клієнтської частини (React/Vite).

---

## 1. Аналіз та оптимізація залежностей

Для ідентифікації "важких" модулів у проект було інтегровано інструмент візуалізації `rollup-plugin-visualizer`.

**Проведені дії:**
- Налаштовано автоматичну генерацію інтерактивної карти бандла при кожній збірці проекту.

**Результат:**
- Виявлено та локалізовано основні джерела об'єму (бібліотеки react-dom, react-router та стилі компонентів).

Аналіз підтвердив відсутність дублювання великих залежностей.

---

## 2. Code Splitting (Розбиття коду)

Замість завантаження всього JS-коду одним монолітним файлом, було впроваджено стратегію завантаження за вимогою.

**Технологія:**
- Використання `React.lazy()` та `Suspense` для маршрутизації на рівні застосунку.

**Реалізація:**
- Модулі додавання аніме (`AddAnimeForm`) та головна галерея (`AnimeList`) винесені в окремі чанки (chunks).

Браузер завантажує код конкретного компонента лише тоді, коли користувач взаємодіє з ним.

**Ефект:**
- Значно зменшено розмір початкового файлу `index.js`, що дозволяє інтерфейсу ставати інтерактивним значно швидше при першому візиті.

---

## 3. Tree Shaking та оптимізація бандлів

Для мінімізації бінарних файлів застосовано механізм видалення "мертвого" коду.

**Tree Shaking:**
- Використовуються суто іменовані імпорти (Named Imports), що дозволяє складальнику Vite видаляти невикористовуваний код із фінальної збірки.

**Стиснення:**
- Кешування запитів до зображень (кастомні постери-плейсхолдери) зменшило кількість побічних HTTP-запитів, значно розвантаживши вкладку Network.

---

## Підтвердження результатів (Build Logs)

Аналіз фінальної збірки (`npm run build`) демонструє чіткий розподіл коду на дрібні, кешовані сегменти, що гарантує лінійну залежність швидкості роботи фронтенду від дій користувача.

# Стрес-тестування та масштабованість (Scalability Test)

Для перевірки ефективності впроваджених оптимізацій (пагінації `PAGE_SIZE=24` та `db_index=True`) було проведено серію тестів на різних обсягах даних.

---

## Методологія тестування

Тестування проводилося за допомогою Django Debug Toolbar (для аналізу SQL та часу бекенду).  
Chrome DevTools Network використовувався для аналізу часу передачі мережею.

---

## Аналіз результатів за сценаріями

### Малий обсяг (100 аніме)
- Базовий рівень продуктивності. Загальний час: **56.95 ms**
- Підтверджено швидкий відгук інтерфейсу (Payload: **17.8 KB**)

### Середній обсяг (1000 аніме)
- Система демонструє стабільність. Загальний час: **89.95 ms**
- Завдяки серверній пагінації, розмір даних не змінився (**17.7 KB**)
- Час виконання SQL (пошук) становить лише **0.42 ms**, що свідчить про ефективну роботу індексів у БД

### Великий обсяг (10000 аніме)
- Критичний тест на масштабованість. Загальний час: **121.80 ms**
- Попри збільшення кількості аніме у 100 разів, розмір переданих JSON-даних залишився константним (**17.9 KB**) — **O(1)**
- Підтверджено часткову деградацію запиту COUNT(*) (час зріс до **7.91 ms**)

---

# Висновки щодо масштабованості

**Стабільність фронтенду:**
- Завдяки серверній пагінації, розмір переданих JSON-даних залишається стабільним (~18 KB)
- Це повністю запобігає "зависанню" інтерфейсу на великих обсягах

**Ефективність індексів:**
- Мінімальний час виконання основних SQL-запитів підтверджує правильність обраної стратегії індексації полів `title`, `genres` та `rating`

# Система моніторингу продуктивності (Application Performance Monitoring)

Для забезпечення безперервного контролю якості сервісу було розроблено та інтегровано кастомну систему APM на базі Django Middleware.

Це дозволяє відстежувати стан системи "в розрізі" кожного запиту, не перевантажуючи сервер зовнішніми агентами.

---

## Технічна реалізація моніторингу

Система базується на розширеному `PerformanceMonitoringMiddleware`, куди було додано функціонал вимірювання латентності (Latency).

### Автоматичний збір метрик
Для кожного вхідного HTTP-запиту фіксується точний час початку та завершення обробки.

### Логування контексту
У журнал `apm_metrics.log` записуються дані у форматі:

```
ENDPOINT | METHOD | PATH | DURATION | STATUS
```

### Точкове профілювання (Critical Ops)
У ViewSet впроваджено роздільне вимірювання часу:
- взаємодії з БД (`Database_Fetch`)
- серіалізації (`Data_Serialization`)

# Аналіз отриманих результатів (згідно з журналом логів)

На основі зібраних даних було проведено аудит критичних операцій застосунку.

## Підтвердження ефективності оптимізації

Після наповнення бази даних (1000+ аніме), запити до основних ендпоінтів демонструють виняткову швидкість:

- Завантаження каталогу: стабілізовано на рівні **~35 ms**
- Обробка пошукових запитів: **~80-90 ms**

Це є прямим доказом того, що впроваджені раніше механізми серверної пагінації та індексування бази даних повністю нівелюють проблеми CPU Bottleneck та перевантаження Payload, забезпечуючи миттєвий відгук інтерфейсу **AnimeGallery**.
